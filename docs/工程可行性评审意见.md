# 接口契约工程可行性评审意见（开发工程师）

> **本周角色产出物**：第 2 周 · 开发工程师——"对接口契约的工程可行性评审意见"。
> **评审对象**：`specs/design.md` v0.4 §4（核心类型、CLI 命令契约、函数级契约、错误码与退出码）。
> **评审视角**：以实际落地过 v1 的工程经验判断每条契约在 Node 22 + TypeScript strict + better-sqlite3 环境下能否实现，不重复红队（测试工程师）对验收口径的评审。
> **评审人**：开发工程师（姜思远）　**日期**：2026-11-26　**结论**：**16 项契约全部可直接落地（无阻塞项）**；其中 2 项（F-07、F-13）建议补充语义约束，以免实现期出现歧义。

---

## 1. 评审范围与方法

| 项 | 内容 |
|---|---|
| 契约总数 | 16 项（核心类型 1 + 时钟 2 + CLI 命令 6 + 函数契约 6 + 退出码 1，按 design.md §4.1～4.3 的核心条目归并计） |
| 方法 | 逐条对照 v1 已实现模块，检查三件事：① 类型在 TS strict 下能否表达；② 错误码与退出码映射是否可实现且不重叠；③ 契约是否与 SQLite/Node API 的实际能力冲突 |
| 判定档位 | 可直接落地 / 需小幅调整（不改语义）/ 阻塞（无法落地或语义冲突） |

## 2. 可直接落地的契约（16 项）

| # | 契约 | 可行性依据 |
|---|---|---|
| F-01 | `Source` / `EntryState` / `ReportStatus` / `AttributionKind` / `LinkType` 五个联合类型 | TS 字符串联合可直接表达，`as const` + `zod.enum` 双校验无歧义；SQL 侧配 `CHECK IN` 即可（v1 已验证） |
| F-02 | `Clock` 端口（`now()` + `timeZone`） | 接口对象在 TS 中天然可注入；`FixedClock` 测试替身成本低，v1 已实践 |
| F-03 | `dayKey(clock, at)` / `dayWindow(clock, date)` | 基于 `Intl.DateTimeFormat` 可实现时区换算，无需第三方时区库；左闭右开窗口可由 `Date` 运算得出 |
| F-04 | `sdr collect --source` 可重复 + `--manual/--ref` 成对 | `commander` 支持 `.option('--source <s>', '...', collect, [])` 累加；成对参数用手工校验即可 |
| F-05 | `sdr collect` 退出码 0/3/4 + 每源一条 `ingestion_run` | `Promise.allSettled` 可得部分失败语义；同批共享 `run_id` 由调用方生成后传入，无需改契约 |
| F-06 | `sdr generate` 无数据返回 0 并输出空白模板 | 这是条件分支而非错误，契约自洽；与 CS-14 一致 |
| F-07 | `sdr edit --accept-attribution --all` 批量确认 | `entry_member` 关联表支持一次事务更新多行；v1 已实现 |
| F-08 | `sdr push --dry-run` 只渲染不发送 | `nodemailer` 支持 `streamTransport` 或跳过 `sendMail`，无技术障碍 |
| F-09 | `sdr history` 权限校验返回退出码 8 | 查询调用者身份与 `manager_id` 即可判定；可见性下沉到仓储层可自证 |
| F-10 | `sdr serve` 常驻进程 | Node 定时器 + 优雅退出（`SIGINT`/`SIGTERM`）标准做法 |
| F-11 | 退出码分段（无 5） | 各码互不重叠；"无数据"不设码的语义正确 |
| F-12 | `collectGithub(opts): Promise<Event[]>` | `fetch` + `AbortSignal.timeout` 可实现；`since/until` 为 `Date` 与时区口径一致 |
| F-13 | `dedupe(events): Event[]` 纯函数 | 无 I/O，易测；`dedupeKey` 可在函数内生成 |
| F-14 | `classifyState(text, rules): {state, confidence}` | 正则规则表驱动，纯函数，可直接单测 |
| F-15 | `assignBlocks(events, blocks)` 返回时间块 | 时段配置从 YAML 读入后为纯计算；休息区间回退规则可用简单比较实现 |
| F-16 | 错误码 `SDR-E1xx`～`E6xx` 与退出码映射 | 分段清晰，E6xx→10 的映射可直接落到顶层错误处理器 |

## 3. 需小幅调整的契约（2 项，不改语义）

| # | 契约 | 问题 | 建议调整 | 是否需改 design.md |
|---|---|---|---|---|
| A-01（对应 F-07 细化） | `sdr edit --accept-attribution [--all]` 与 `--add-text`/`--remove-entry` 共用一命令 | 单条编辑与批量确认混在同一命令，参数组合合法性需额外校验（如 `--all` 与 `--add-text` 同时给出时应报错） | 在 design.md §4.2 补一行"参数互斥规则：`--all` 不与 `--add-text`/`--remove-entry` 同用，违反时退出码 2" | 是（补语义约束，不改命令结构） |
| A-02（对应 F-13 细化） | `dedupe(events): Event[]` 返回类型未说明`run_id` 与 `dedupeKey` 的写入时机 | 纯函数若同时负责生成 `run_id` 会破坏可测性（每次调用结果不同）；但采集器需要它来写 `ingestion_run` | 明确 `run_id` 由 CLI 编排层生成并注入 `Event`；`dedupe` 只按已有 `dedupeKey` 合并，不生成新键 | 是（补职责边界，不改签名） |

> 两项调整均属"补语义约束"，不改变 design.md 已声明的函数签名或 CLI 命令结构，故不构成对上游规范的偏离，无需回写 proposal.md 的验收标准。

## 4. 结论与移交

- **无阻塞项**：design.md §4 的接口契约在既定技术栈下全部可实现，v1 的实践已覆盖其中绝大多数路径。
- **给 v2 的建议**：A-01、A-02 两项在 v2 重新设计契约时直接从一开始就写清，可省掉 v1 的补丁式修正。
- **移交测试工程师**：本评审只判断"能不能实现"，不判断"验收标准是否可测"；后者见 `docs/验收标准可测性评审意见.md`。
