## 1. 项目名称

**智能日报生成器（Smart Daily Report Generator）**，代号 `sdr`。

一句话定位：从成员的真实工作数据中自动生成个人日报，并汇总为格式统一的团队日报，经邮件推送。

---

## 2. 目标（可度量）

| 编号 | 目标 | 度量方式 |
|---|---|---|
| G-01 | 消除手工回忆与跨平台复制粘贴 | 单成员单日**手工新增或改写**条目数 ≤ 1 条；数据源覆盖 ≥ 2 个平台（GitHub、飞书任务）。归属批量确认（`sdr edit --accept-attribution --all`，一次调用）属审阅动作，不计入该指标 |
| G-02 | 降低遗漏率 | 当日有提交或任务流转的成员，其日报条目完整率 ≥ 95%（以源数据事件数为基准） |
| G-03 | 协作成果自动归属 | 有 `Co-authored-by` 标记时，条目须归属到全部标记作者（命中率 100%）；协作条目总数占多作者提交的比例 ≥ 80%（含兜底归属，兜底项须带 `[待确认]` 并可确认） |
| G-04 | 格式统一，免除组长手工汇总 | 团队日报由系统一次生成，无需人工排版；汇总耗时从〔基线：待实测〕降至 0 人工操作 |
| G-05 | 生成时延可接受 | 单成员日报生成 ≤ 30 秒（P95，不含外部 API 重试等待） |

> G-03 的 80% 为目标值，实际覆盖率受团队提交习惯影响；若实测低于该值，须在 design.md 的 ADR 中记录兜底策略的取舍。

## 3. 背景

团队成员每日需手工撰写工作日报。本章先交代调研方法与结论，再给出痛点与系统解法的对应关系。

### 3.1 调研方法与对象

采用结构化访谈（18 个问题，覆盖数据源、读者、粒度、协作归属、异常、合规、运行七个维度），对象为产品研发类小团队（3–8 人）。原始问答记录见 `backup/业务调研纪要.docx`，本节的每条结论均可回溯至具体问题编号（Q1～Q18）。

### 3.2 访谈结论（18 项）

| 编号 | 议题 | 访谈结论 | 对设计的约束 |
|---|---|---|---|
| Q1 | 数据源 | GitHub 提交、飞书任务、QQ/微信、本地文件 | 采集层需四类适配器 |
| Q2 | 接口能力 | GitHub、飞书有开放 API；QQ/微信仅手工补充 | 群聊自动采集排除（EX-01、EX-02） |
| Q3 | 主源判定 | 以 GitHub 与本地最终结果为主，允许去重合并 | 需事件归一与去重（FR-05） |
| Q4 | 非结构化数据 | 需纳入，采用关键词提取 | 需关键词库与置信度（FR-06） |
| Q5 | 读者 | 直属上级逐份阅读 + 团队汇总 | 需单人与汇总两种视图（FR-10） |
| Q6 | 关注点 | 关心"做了什么"（成果），非计划 | 成果字段权重高于计划字段 |
| Q7 | 粒度 | 按休息时间分割时间块 | 需定义休息时段来源（§5.1） |
| Q8 | 结构 | 区分不同字段，按时间段呈现不同阶段 | 时段 × 状态二维结构（FR-07） |
| Q9 | 语体 | 去人称陈述 | 模板禁用第一人称（CS-05） |
| Q10 | 协作归属 | 按 Co-authored-by 标记归属 | 需兜底规则（ADR-004） |
| Q11 | 归属展示 | 不需过多展示，给出概况或结果链接 | 每条附来源链接（CS-04） |
| Q12 | 软性贡献 | 以 QQ/微信对话体现 | 依赖手工摘录（FR-04） |
| Q13 | 缺勤 | 生成请假占位 | 与空白日报语义须区分（IR-01） |
| Q14 | 无进展日 | 允许生成空白日报，可自行添加 | 需可编辑态（CS-06、CS-14） |
| Q15 | 采集失败 | 标注具体原因并邮件告警 | 需错误分类与告警（FR-09） |
| Q16 | 留存与可见性 | 永久保留；仅本人与直属上级可见；不脱敏 | 与汇总视图冲突，见 R6 |
| Q17 | 知情同意 | 成员同意工作痕迹被采集 | 需 consent 记录（技术约束） |
| Q18 | 推送 | 邮件推送，时间可配置，错过补发 | 需调度器 + 补发（FR-11） |

> 访谈结论直接导出 9 条原始需求基线，经拆解后形成 §4.1 的 FR-01～FR-12。二者的对应关系：原 FR-01（采集）拆为 FR-01～FR-04，原 FR-05（异常）拆为 FR-09，其余一一对应。

### 3.3 痛点与系统解法

痛点与系统解法的对应关系如下（对照课程第一部分列出的五个痛点）：

| 痛点 | 具体表现 | 系统解法 | 对应范围编号 |
|---|---|---|---|
| ① 记忆翻找 | 下班时回忆"今天干了什么"，依赖记忆 | 自动采集提交与任务流转，由事件驱动生成条目 | FR-01、FR-07 |
| ② 跨平台复制粘贴 | 痕迹散落在 GitHub、飞书、群聊，逐条搬运 | 多源适配器统一采集 + 事件归一 | FR-01～FR-05 |
| ③ 必然遗漏 | 写进去的是"记得住的"，不是"做了的" | 以源数据为基础生成，条目完整率可度量（G-02） | FR-05、FR-07 |
| ④ 协作成果无人记 | 帮同事改的接口、一起修的缺陷谁都没写 | 依据提交作者与 Co-authored-by 自动归属，附结果链接 | FR-08 |
| ⑤ 格式不统一 | 每人格式不同，组长手工汇总 | 统一模板生成 + 团队汇总视图 | FR-07、FR-10 |

结论：五个痛点中，①与②由采集层消除，③由"源数据驱动生成"消除，④由归属策略消除（但受 R3 影响，覆盖率不完全），⑤由模板与汇总消除。**没有任何一个痛点可仅靠 UI 改善解决，这构成了排除图形界面的依据（EX-03）。**

## 4. 范围

### 4.1 做什么（逐条编号，供用例追溯）

| 编号 | 范围项 | 说明 |
|---|---|---|
| FR-01 | GitHub 提交采集 | 通过 GitHub REST API 拉取指定仓库在统计窗口内的提交（作者、时间、变更文件、提交信息、关联 PR） |
| FR-02 | 飞书任务采集 | 通过飞书开放平台接口拉取任务流转记录（创建、状态变更、完成时间、负责人） |
| FR-03 | 本地文件变更采集 | 扫描配置的本地目录，按修改时间识别当日产出文件 |
| FR-04 | 手工补充入口 | 命令行录入条目，用于采集不到的信息（群聊沟通、会议、答疑等软性贡献） |
| FR-05 | 事件归一与去重 | 同一事件的多源痕迹合并为一条（主源：GitHub 提交与本地最终产出；辅助源：飞书任务状态） |
| FR-06 | 关键词提取 | 对非结构化文本（提交信息、手工补充）按关键词库识别进展阶段 |
| FR-07 | 日报生成 | 按休息时间划分时段，生成"时段 × 状态（完成/进行中/计划/阻塞）"结构的去人称日报 |
| FR-08 | 协作归属 | 依据提交作者与 Co-authored-by 标记归属；每条附结果链接（提交地址或文件路径） |
| FR-09 | 异常处理 | 请假生成占位条目；无进展生成可编辑空白日报；凭证失效标注原因并发邮件告警 |
| FR-10 | 团队汇总 | 将全组成员日报汇为一份团队日报，格式统一 |
| FR-11 | 邮件推送 | 按可配置时间推送；错过时点自动补发 |
| FR-12 | 历史存储 | SQLite 持久化日报，永久保留，支持按人按日查询 |

### 4.2 不做什么（本期明确排除，逐条给出理由）

本清单为评分点，每条均须给出排除理由，并说明留待版本。

| 编号 | 排除项 | 排除理由 | 去向 |
|---|---|---|---|
| EX-01 | **QQ / 微信聊天记录的自动采集** | 两类产品均无面向第三方的开放消息接口，非官方手段抓取存在个人信息合规风险；且群聊内容超出"工作痕迹"的合理采集范围。本期仅提供手工补充入口（FR-04）承载软性贡献。 | 不纳入路线图 |
| EX-02 | **飞书消息的自动采集** | 飞书消息接口需企业自建应用授权与管理员审批，个人开发者账号无法取得；本期以飞书任务（有开放接口）替代，消息内容走手工补充。 | 视授权可得性再议 |
| EX-03 | **图形界面（Web / 桌面）** | 本期交付形态为命令行工具 + 邮件输出，界面设计不产生方法论文档价值的增量，却会挤占 4 周内两套实现（v1-SDD、v2-Superpowers）的工期。 | v1.1 再议 |
| EX-04 | **LLM 生成式摘要与措辞润色** | v1 采用规则模板拼接，保证输出可复现、可解释、可测试；引入生成式改写会使条目来源不可追溯，与"归属可核验"目标冲突。 | v1.1 再议 |
| EX-05 | **考勤系统对接** | 依赖外部考勤系统授权且超出课程周期；请假状态由成员手工标记（FR-09 的占位条目）替代。 | v1.1 再议（对应教材 7.5 节迭代示例） |
| EX-06 | **统计报表与趋势分析** | 日报永久存储但不提供分析视图（FR-12 仅保证可查询），避免与"生成"主目标争夺工期。 | 不纳入本期 |
| EX-07 | **多团队 / 多租户与细粒度权限体系** | 本期服务于单个研发团队，权限简化为"本人 + 直属上级可见"（见 §6 CS-09），引入 RBAC 属过度设计。 | 不纳入路线图 |
| EX-08 | **HTML 版邮件正文** | 纯文本正文已满足"格式统一、可直接阅读"的验收要求；HTML 版式需额外模板与跨客户端兼容测试，收益低于其占用的工期（第 2 周工时超支时的首个削减项，见 tasks.md 削减策略）。 | v1.1 再议 |

> 说明：EX-01 与 EX-02 同时是调研阶段识别出的高风险项（纪要 R1）。写入"不做什么"意味着它是一项经决策的排除，而非遗漏。

## 5. 技术约束

| 类别 | 约束 |
|---|---|
| 语言 | **TypeScript 5.x（`strict` 模式）**，禁止隐式 `any`，`tsc --noEmit` 必须零错误 |
| 依赖与运行 | Node.js ≥ 22 LTS；`pnpm` 管理依赖；命令行入口，无 GUI 依赖 |
| 数据库 | SQLite（单文件，`data/` 目录下，不入仓） |
| 外部依赖 | GitHub REST API、飞书开放平台 API、SMTP 邮件服务 |
| 凭证管理 | Token / 飞书凭证 / SMTP 授权码一律通过环境变量注入，禁止写入代码与仓库；`.env.example` 只放键名 |
| 运行环境 | macOS / Linux 命令行（Node 单进程）；无容器化要求 |
| 数据合规 | 采集前须取得成员知情同意并留痕；日报内容不脱敏但仅限本人与直属上级可见（见 §6 CS-09）；相关代码属课程 AI 四色清单中的红线区，须人工审查并留痕 |
| 时区与日历 | 以本地时区（Asia/Shanghai）为准；休息时段定义须可配置，不硬编码 |

> 语言选型说明：本期采用 TypeScript 而非 Python。理由为采集层与 CLI 的异步 I/O 模型统一、`tsc strict` 对 AI 生成代码的约束力更强（类型错误在编译期暴露，而非运行期），且测试打桩可用原生 `fetch` 拦截完成。该决策不改变任何 FR / CS 条目，仅改变实现形态。


### 5.1 待决策项（移交 design.md 以 ADR 形式确定）

1. 飞书任务相对 GitHub 提交的取舍权重（§8 R2）
2. Co-authored-by 缺失时的归属兜底规则（§8 R3）——候选：同一文件路径历史作者 / 时间窗重叠 / 人工认领
3. 休息时段的来源与默认值（工作时间配置项）
4. 团队汇总视图的聚合粒度（§8 R6）——建议仅呈现条目数与时段的聚合结果，不展开他人明细

### 5.2 术语定义

| 术语 | 定义 |
|---|---|
| 事件（Event） | 一次可被采集的工作痕迹，如一次提交、一次任务状态变更、一次文件保存 |
| 条目（Entry） | 日报中的一行成果陈述，由一条或多条事件经归一与生成后形成 |
| 主源 / 辅助源 | 主源决定事件是否成立（GitHub 提交、本地最终产出）；辅助源只补充状态与上下文（飞书任务） |
| 去人称 | 日报陈述不出现"我/我们"，采用动宾结构，如"完成登录接口鉴权改造" |
| 时段 | 按休息时间划分的时间块（如上午 / 下午），条目按发生时段归位 |
| 占位条目 | 表示未出勤的固定条目（请假、调休、出差），与"空白日报"（出勤无进展）语义不同 |
| 来源标识 | 条目可追溯的凭据，三种形态：提交链接（`url`）、文件路径（`path`）、手工录入时的来源说明（`note`，如"飞书群聊 11-25 15:30 讨论接口"） |
| 待确认归属 | 兜底规则无法确定协作成员时，条目以 `[待确认]` 前缀标记，待成员一次性确认的归属状态 |
| 统计窗口 | 一次生成所覆盖的时间范围，默认当日 00:00 至推送时刻（Asia/Shanghai） |

## 6. 成功标准

### 6.1 功能验收

| 编号 | 验收标准（可度量） |
|---|---|
| CS-01 | 给定含 ≥ 5 条提交、≥ 3 条任务流转的测试数据，单次生成输出条目数 ≥ 输入事件数的 80%，且同一提交不重复出现（去重准确率 100%） |
| CS-02 | 日报条目按休息时段正确归位，错误归位率 ≤ 5% |
| CS-03 | 含 Co-authored-by 标记的多作者提交，条目须为**每一位**标记作者各建立一条归属记录（主责 1 人 + 协作 N 人），命中率 100%；兜底归属（任务时间窗 / 无法判定）的条目须带 `[待确认]` 标记，并可经一次批量命令确认 |
| CS-04 | 每条条目均附**来源标识**：提交链接或文件路径（`url`/`path`），手工条目附录入时必填的来源说明（`note`，如"飞书群聊 11-25 15:30 与张三讨论接口"）；来源标识缺失率为 0 |
| CS-05 | 日报正文不出现第一人称代词（"我""我们"），命中数为 0 |
| CS-06 | 标记请假后，当日输出占位条目而非空文件；未标记且无事件时，输出可编辑的空白日报模板 |
| CS-07 | 凭证失效时，输出标注具体错误类型（如 401、令牌过期），并触发一封告警邮件；其余数据源采集不中断 |
| CS-08 | 推送时间修改后，下次推送按新时间执行；模拟错过时点，补发在 5 分钟内完成 |
| CS-09 | 以成员 A 身份查询时，无法取得成员 B 的日报明细；团队汇总仅含聚合信息（出勤状态、条目计数、状态分布）与定位信息（成员 + 日期 + 查看命令），**不含任何条目的正文** |
| CS-10 | 日报历史在服务重启后仍可查询，按人按日检索响应 ≤ 2 秒（数据量 ≤ 1000 条） |

### 6.2 性能验收

| 编号 | 指标 |
|---|---|
| CS-11 | 单成员单日生成（含 3 个数据源采集）≤ 30 秒（P95，网络正常） |
| CS-12 | 团队汇总（≤ 10 人）≤ 60 秒 |
| CS-13 | 单次生成对 GitHub / 飞书 API 的调用不超过各自速率限制的 50% |

### 6.3 边界场景

| 编号 | 场景 | 期望行为 |
|---|---|---|
| CS-14 | 当日无任何采集数据 | 生成空白日报模板，可手工添加，不报错 |
| CS-15 | 同一提交在两次生成中被重复采集 | 去重后仅出现一次 |
| CS-16 | 跨天任务（前一日开始、当日完成） | 完成条目计入完成日（`report_date`），起始日期记于 `entry.original_date`，并在正文前缀标注"（自 MM-DD 起）" |
| CS-17 | 外部 API 超时 | 重试不超过 3 次，失败后标注该源缺失，不影响其他源 |
| CS-18 | 成员当日请假且有提交记录 | 输出占位条目，同时保留该提交条目并提示冲突，由成员确认 |
| CS-19 | UTC 时间 16:00 之后发生的提交（即 Asia/Shanghai 次日 00:00 之后） | 计入其对应的本地日期；同一提交重复采集时去重键一致，不产生跨日重复条目 |

## 7. 隐含需求（访谈中被问出来的，非原始需求）

以下 8 条在需求澄清的 18 问中浮现，原始任务描述未提及，但缺其一即无法交付：

| 编号 | 隐含需求 | 来源问题 | 为何必需 |
|---|---|---|---|
| IR-01 | 请假占位与空白日报必须是两种不同状态 | Q13、Q14 | 若混同，团队汇总出勤率与产出率统计失真 |
| IR-02 | 采集失败必须显式标注原因并告警，不得静默跳过 | Q15 | 静默失败会让成员误以为"今天没事做"，直接摧毁信任 |
| IR-03 | 推送时间可配置 + 错过时点补发 | Q18 | 单一固定时点无法适配加班与出差场景，漏推等于当天日报作废 |
| IR-04 | 日报语体须去人称 | Q9 | 团队汇总需拼接多人条目，人称冗余无法合并 |
| IR-05 | 按休息时间划分时段，而非按自然小时 | Q7、Q8 | 午休跨越会使条目归属到错误时段，影响"上午/下午"叙事 |
| IR-06 | 归属结果须可追溯到具体产出（链接或路径） | Q11 | 成员会质疑归属准确性，无依据则工具不可信 |
| IR-07 | 团队汇总不得展开他人日报明细 | Q16 + Q5 | 汇总需求与"仅上级与本人可见"直接冲突，须以聚合化解 |
| IR-08 | 日报需永久保留并可按人按日检索 | Q16 | 周会、绩效沟通需回看历史，且课程要求证据可追溯 |

## 8. 风险与待确认项

以下 6 项由访谈结论的内在冲突识别得出，非凭空推测。标注为"高"者须在第 2 周阶段评审前给出结论。

| 编号 | 风险 | 等级 | 说明与处置方向 |
|---|---|---|---|
| R1 | 群聊采集链路不可行 | 高 | Q1、Q2、Q12 相互依赖：群聊被列为数据源且承担软性贡献的体现，但无开放 API。已在 EX-01、EX-02 中显式排除，v1 以手工补充入口（FR-04）承载；须与指导教师确认课程允许的采集方式。 |
| R2 | 主源优先级未量化 | 中 | Q3 以 GitHub 与本地结果为主，但飞书任务的取舍权重未定。处置：同一事件多源命中时保留本地产出，飞书任务仅补充状态（已写入 design.md ADR-002 的去重规则）。 |
| R3 | 协作归属覆盖率不足 | 高 | Q10 仅依赖 Co-authored-by，实际提交中该标记出现率偏低，将导致大量成果无归属，G-03 的 80% 目标无法达成。处置：采用三级兜底（design.md ADR-004）；归属由 `entry_member` 关联表承载，一条条目可归属多人，仍无法判定者标 `[待确认]` 并经 `--accept-attribution --all` 一次批量确认；"待确认条目占比"纳入第 4 周质量数据。 |
| R4 | 可解释性与信任 | 中 | Q11 要求"不需过多展示"，与成员可能质疑归属存在张力。处置：每条保留一行来源标识（成本极低），并以 `entry.attribution_kind` 记录归属依据（标记 / 任务时间窗 / 兜底），不做权重解释。 |
| R5 | 请假占位与空白日报语义重叠 | 中 | Q13、Q14 分别要求两种输出，若混同则汇总统计口径失真。处置：数据模型中以 `report.status` 的 `leave` 与 `blank` 区分（IR-01）。 |
| R6 | 隐私与可见性冲突 | 高 | Q16 的"永久保留 + 不脱敏"与"仅上级与本人可见"同 Q5 的团队汇总需求矛盾：汇总若含明细则突破可见边界。处置：汇总只呈现出勤矩阵、条目计数与状态分布、阻塞项**定位信息**（成员 + 日期 + 查看命令），不含任何条目正文；可见性在数据访问层以投影白名单实现（design.md ADR-006）。此项涉及课程 AI 四色清单的隐私红线，相关代码须人工审查并留痕；**不得以"为可用性开例外"的方式放宽 CS-09**。 |

**风险与范围的关系**：R1 已由 EX-01、EX-02 转化为显式排除决策；R3、R6 不改变范围，但改变了 §6 验收标准的实现方式（CS-03 的兜底、CS-09 的聚合口径）；R2、R5 已下沉到 design.md 的 ADR 与数据模型中解决。
